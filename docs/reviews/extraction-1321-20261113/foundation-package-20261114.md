**Policy-DDL steps (D2, D4, D6, D7, D9): how to send and when.** Each is one transaction: `begin`, its own `lock_timeout` (D2 3 s; D4, D6, D7 2 s; D9 1 s), `statement_timeout` 60 s, a fixed `search_path`, `lock table … in share update exclusive mode`, and only then the guard. `CREATE` / `ALTER` / `DROP POLICY` need `ACCESS EXCLUSIVE` on the table (measured on PostgreSQL 16 and 17): the statement waits for the readers that are running, new readers queue behind it, for at most the lock timeout; on `lock timeout` nothing has changed and the same file is sent again. Send each in a quiet minute (D9 touches `storage.objects`, the busiest of them, hence 1 s). `GRANT` / `REVOKE` take no table lock, so a privilege change committed by another session between the guard and the commit is not excluded by the lock; the postcondition sees any such change committed before it.
