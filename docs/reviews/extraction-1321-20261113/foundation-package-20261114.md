## 2. What changed since the last report

* **CR-F1 — CL-16 apply and rollback overwrote a concurrent trigger change (Codex P2, blocked D10).** Reproduced independently by Codex on PostgreSQL 17.12 and again here with a barrier-based harness: session B opens `ALTER TABLE public.nodes DISABLE TRIGGER trg_rule_compaction_integrity_guard_v1`; while B's change is uncommitted, the real apply (or rollback) starts and waits; B commits; the file then continues and `CREATE OR REPLACE TRIGGER` re-enables the trigger B disabled, and both postconditions pass. **Fix (#1343):** `lock table public.nodes in share row exclusive mode;` as the first statement after the timeouts in both files — the mode that `CREATE [OR REPLACE] TRIGGER` and `ALTER TABLE ... DISABLE TRIGGER` take themselves — so a concurrent change is either committed first (the unchanged checks see it and refuse on drift) or still open (the file waits for at most the 5 s lock timeout and then fails with nothing changed). The static drift protections, the postconditions and the rollback metadata behaviour are untouched. **Tests** (the existing runner `scripts/run-g1-rule-guard-sql-test.sh`; no new file, so the package-scope pins stand): nine concurrency cases, each in its own database, each with a second session holding an open change and a barrier on `pg_stat_activity` / `pg_locks` (no sleep decides the order): **A1 / R1** the race for the apply and for the rollback (the file refuses; the trigger stays disabled; nothing else changed); **A2 / R2** clean runs after waiting; **A4 / R4** Codex's control (a concurrent `CREATE OR REPLACE FUNCTION` makes the file fail with `tuple concurrently updated`, B's body is preserved); **A5** readers; **A3** writers and an atomic lock timeout; **R3** readers and an atomic lock timeout of the rollback's `DROP TRIGGER`. **Measured lock impact** (PostgreSQL 16 and 17): readers of `public.nodes` are never blocked by the apply (a plain read answered in about 15–20 ms while the apply waited); writers wait behind the lock request for at most the lock timeout (a second writer queued about 5.0 s and then went through); in the rollback `DROP TRIGGER` needs `ACCESS EXCLUSIVE`, so there new readers queue for at most the lock timeout (about 5.0 s) and a timeout rolls back **everything** the file did. Self-check: the same cases run against the files before the fix (`G1_RG_CC_APPLY` / `G1_RG_CC_ROLLBACK`) make A1 and R1 fail and the runner exit 1.
* **CR-F2 — the Docker fallback of the `contribution_links` runner could not find its SQL files (Codex P3).** It mounted the temporary folder at `/w` but passed host paths into the container, so it stopped at the first call ("No such file or directory") before any test ran. **Fix (#1340):** the folder is mounted at the same path (`-v "$W:$W:ro" -w "$W"`), so the host paths it passes — also the generated foreground and background SQL files — exist in the container, and a visibility check runs before the first psql call. No SQL file or assertion changed. **Proof through a real Docker daemon** (Docker 29.9.2, `postgres:17-alpine`, network-less container; the native PostgreSQL binaries hidden from the runner by a private mount namespace so that it chooses its Docker branch): the previous version fails at the first call, exit 1; the fixed version runs **9 SQL + 5 concurrency cases** and exits 0.
