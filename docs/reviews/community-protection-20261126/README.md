## 2. קישור הודעה לרשת, בפרטיות
* **מקור מהימן:** הכותרת `cf-connecting-ip` שהפלטפורמה קובעת (Cloudflare מחליפה כל ערך שהלקוח שולח; כל בקשות Supabase עוברות דרכה, ראו `edge_logs`). זה כבר מה ש־`add_guest_community_message` מעדיף כיום. החלופות `x-real-ip` ו־`x-forwarded-for` קיימות בקוד הקיים כגיבוי; בלקוח הם ניתנים להזיה, והן נשארות כפי שהן (לא הורחבו).
* **מה נשמר:** hash מפתח (SHA-256 עם מפתח אקראי שנשמר בטבלה שאיש אינו יכול לקרוא) של הכתובת הגסה: IPv4 כמות שהיא, IPv6 לפי /64. הכתובת הגולמית נשארת משתנה זמני בתוך הפונקציה ואינה נכתבת. בנוסף, **מהיום** יומן ההגבלה הקיים `anon_contrib_log.ip` מקבל את ה־hash במקום הכתובת (ללא שינוי בלוגיקת ההגבלה). שורות גולמיות קיימות (43 ביום הבדיקה) נשארות כפי שהן; **מחיקתן היא החלטה נפרדת** (אינה כלולה).
* **הודעות היסטוריות:** `community_guest_posts` כולל 42 הודעות שנכתבו לפני ההצעה. אין לאף אחת הפניית רשת, ולא ניחשתי: ללא התאמת זמנים ל־`anon_contrib_log`. ניסיון לחסום לפי הודעה כזו נכשל ב־`no_network_reference`. רק הודעות שייכתבו אחרי ההחלה ניתנות לחסימה.
* **סיבוב מפתח:** החלפת המפתח מבטלת בפועל חסימות קיימות ולכן אינה חלק מההצעה.

## 4. מהירות
* אין שינוי בקריאה, באינדוקס, בשער או ב־shell. העבודה הנוספת היא בכתיבת אורח בלבד: hash אחד וחיפוש אחד באינדקס חלקי (`net_ref` של חסימה פתוחה). נמדד על Postgres מקומי: **כ־11 מיקרו־שנייה לצמד (hash + בדיקה)**, בתוך בקשה שכבר כוללת כמה כתיבות ושאילתות.
* הלקוח: קובץ API קטן (`communityNetBlocksApi.js`) שנטען רק בפאנל הצוות, שכבר נטען למנהלים בלבד; אפס ייבוא סטטי חדש בכניסה או במסגרת.
