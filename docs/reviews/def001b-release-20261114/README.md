# DEF-001b — שני צעדי מסד, בקשת החלה ממוקדת

מצב: **מוכן לביקורת; לא הוחל**. בסיס קוד: `9c4cad1372200759e9afe6e9c38709209d4ee02a`. הפריסה החיה שנקראה מחדש: `dpl_89Men3jqSi3pAJ5jGMpp75iZqDzx`.

זו אריזת הפעלה לשני קובצי SQL שכבר נמצאים ב-main: צעדים 1 ו-9 של #1334. אין כאן שינוי בקוד האתר או ב-Edge, ואין תלות במיזוג #1334 כולו. בעלים קיימים: `person_foundation_contract_law` v6, ובגבול ערוץ ההתראות `subscription_funnel_law` v22. אין חוק, טבלה או מאגר חדשים בחי.

## מה משתנה

1. `01-prepare.sql`: המשוב נקרא רק בידי מנהל; מזהה המבקר מוסתר בעמודת `els_records.visitor_id`; שאר עמודות ELS נשארות כפופות למדיניות השורות הקיימת. שתי פונקציות הרשמה/ביטול Push מתווספות. גישת האורח הישירה לטבלת Push נשארת פתוחה בשלב זה כדי לאפשר מעבר.
2. `02-lockdown.sql`: אחרי אישור זמינות שתי הפונקציות ב-API, מסיר את ארבע מדיניות האורח ואת הרשאותיו הישירות לטבלת Push. הרשמת Push עוברת בפונקציות הקיימות בקוד האתר. הרשאות המשתמש המחובר על הרשומות שלו ושירות השרת נשמרות.

אין מחיקת נתונים, שיגור התראות, קמפיין או שינוי זכאות למנויים. כל קריאת נתוני בדיקה נותרת מוגבלת; לא הורדו נתוני משתמשים מהחי.

## ההבדל מקובצי המקור

קובצי המקור נותרו זהים בבתים. ההרכבה מקבעת SHA-256 לכל אחד ומסרבת לשינוי בלתי-סקור. הקבצים המורכבים מוסיפים:

- טרנזקציה נפרדת לכל צעד, נעילות על שלוש הטבלאות, `lock_timeout=5s` ו-`statement_timeout=60s` לכל פקודה. הנעילה יכולה לעכב קריאה וכתיבה לזמן ההחלה הקצר; לא מובטח אפס עיכוב.
- בדיקת מצב לפני ואחרי: הגדרות העמודות וברירות המחדל, הבעלים, grants ברמת טבלה ועמודה, RLS/policies ושתי פונקציות ה-RPC (גוף, חתימה, דגלים והרשאות). אין טענה לכיסוי סמנטי של אובייקטים אחרים.
- אימות שקיים אינדקס unique תקף ולא חלקי על endpoint, לפני כל צעד קדימה.
- בקשת רענון schema ל-PostgREST באמצעות NOTIFY, שנמסרת רק אם הטרנזקציה נשלמה.
- ב-rollback בלבד: החזרת הרשאת MAINTAIN לאורח על טבלת Push, שהייתה בחי ומושמטת בקובץ המקורי. זו החזרה מדויקת של המצב שנבדק, לא המלצה לתת אותה במצב הסופי.

`pg_temp.def001b_catalogue_md5` היא פונקציה זמנית לבדיקה בלבד; היא נמחקת לפני commit. לא נשמר אובייקט חדש לתיאום/אכיפה.

## ראיות

`before.json` הוא צילום קטלוג בלבד מהחי ב-14.11; אין בו שורות מוצר או מפתחות. אותו מצב שוחזר מקומית ונתן אותה חותמת קטלוג בדיוק. `phase-hashes.json` נועל גם את המצב אחרי כל אחד משני הצעדים. שינויים בלתי צפויים גורמים לסירוב ולביטול הטרנזקציה; הרצה חוזרת אינה מדווחת כהצלחה שקטה.

- PostgreSQL 17.12 מבודד, ללא רשת: 23/23 תרחישי החבילה, כולל חזרה אחרי כל אחד משני השלבים, שמירת נתונים, סדר שגוי, drift של ACL/בעלים/RLS/מדיניות/עמודות/פונקציה, כשל מאוחר ובדיקות שבירה מכוונת.
- חמש בדיקות SQL קיימות נשארות ירוקות: DEF-001, DEF-001b, DEF-004, DEF-005, DEF-003.
- 36 בדיקות קוד וקישורי workflow עברו; G1 עבר 51/51.
- ה-API החי במצב BEFORE נבדק בקריאה בלבד. אין כאן הרשמת Push אמיתית או הוכחת מסירת התראה.
- כשל ראשון בהרצת סביבת בדיקה נבע ממקום בדיסק. פונו עותקי worktree נקיים וזמניים שנוצרו לביקורת; שום ענף או קומיט לא נמחק. הבדיקות עברו לאחר הפינוי.

המריץ הקיים `scripts/run-def001-sql-test.sh` מריץ גם את בדיקות החבילה, ולכן ה-CI הקיים מבצע אותן בלי workflow חדש. תוצאת CI תקפה רק ל-SHA המוגש; תוצאה מקומית אינה CI.

## סדר ההפעלה — אחרי אישור לקומיט ולחותמות

1. לקרוא שוב main, הפריסה והיומן. להריץ `node scripts/def001b-release-packet.mjs --check`. לעבוד רק מול הפרויקט `linswmnnkjxvweumprav` והקבצים המקושרים לקומיט המאושר.
2. להריץ `verify.sql` בקריאה בלבד: חייב להיות BEFORE. לקרוא ולתעד מדדי בסיס ללא תוכן אישי. חוסר התאמה = עצירה; לא מרעננים חותמות כדי לעבור.
3. להריץ את **כל** `01-prepare.sql` בבקשה אחת; לא לפצל פקודות. האישור הוא לקובץ המורכב, ולא לקובץ המקור הלא-מוגן. השינוי נשלם רק אם בדיקת המצב שאחריו עוברת.
4. להריץ `verify.sql`: PREPARED_API_CHECK_REQUIRED. להריץ `NODE_USE_ENV_PROXY=1 node scripts/verify-def001b-public-api.mjs prepared`.
   - בדיקת API משתמשת ב-GET בלבד. פרמטר מכוון שאינו בחתימה גורם ל-PGRST202 לפני ביצוע הפונקציה; הרמז צריך להכיל את החתימה המדויקת. אין ניסיון קריאה תקין ל-RPC.
   - OpenAPI מוגבל למפתח שירות, ו-OPTIONS מחזיר 200 גם לפונקציה שאינה קיימת; לכן הם אינם הוכחה. לא משתמשים במפתח שירות בדפדפן/סביבת הבדיקה.
   - אם החתימה לא מוכחת, נשארים בשלב 1 ומדווחים; לא ממשיכים לנעילה ולא מריצים מחדש SQL. הבדיקה מחמירה ועלולה להישאר חסומה אם ה-API לא מחזיר רמז חתימה.
5. רק כשהבדיקה עוברת, להריץ את **כל** `02-lockdown.sql` בבקשה אחת. אחריו `verify.sql` חייב להחזיר LOCKED ובדיקת API עם `locked` חייבת לעבור.
6. לקרוא שוב את האתר ומנועי הקריאה הציבורית, לדווח בדיקות שעברו ומה לא נבדק, ולכתוב AFTER פסיבי באותה רשומת יומן. אין בהחלה הזאת מיזוג או פריסת אתר.

## חזרה במקרה כשל

`rollback.sql` מקבל רק את המצב המדויק PREPARED או LOCKED; אם מישהו שינה אובייקט מכוסה, הוא מסרב לפני שינוי. הוא מחזיר את כל קטלוג ההרשאות המכוסה ל-BEFORE ומוכיח זאת בתוך אותה טרנזקציה. הוא אינו מוחק שורות, מנויים, משוב או ELS. הוא כן מחזיר את הקריאה הרחבה והרשאות האורח הישנות; זו משמעות חזרה למצב הקודם.

לאחר חזרה: `verify.sql` חייב להחזיר BEFORE; בדיקת API `before` מוכיחה שרענון schema הסתיים. עד רענון ה-cache ייתכן כשל זמני ב-Push. אם guard של rollback מסרב בגלל שינוי מקביל, עוצרים ומציגים את המצב, ולא עוקפים אותו.
