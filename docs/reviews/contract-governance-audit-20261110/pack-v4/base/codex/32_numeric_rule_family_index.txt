—— NUMERIC QUERY NORMALIZATION FANOUT · Human-Gate ZURIEL · 8.9.2026 ——

This extends the existing Numeric Research Rule Family / number-reading infrastructure only. No new engine/store/registry.

When a user/researcher queries a number N, the research response should fan out through all applicable GOVERNED numeric readings while preserving the raw input as the primary identity. At minimum, evaluate separately:
1) EXACT N — direct engine/corpus matches for N.
2) LEADING-ONE / THOUSAND REMAINDER when applicable under shitat_haechad_alef_law: 1xyz → xyz as an interpretive transform (example: 1456 → 456), preserving 1456 as raw input.
3) ZERO-SCALE family under zero_scale_law / zero_navigation: N×10 and, where exact trailing zero exists, N÷10; recursively/boundedly where useful (example: 456 ↔ 4560; 45600 is same root family but must be ranked, not dumped blindly).
4) DIGIT / OVERLAPPING READINGS already stored in number_readings (example: 45→56→456 overlapping reading).
5) Other active System Methods / numeric research laws only when their applicability conditions are actually met.

Truth boundary: NORMALIZATION/TRANSFORM ≠ GEMATRIA ENGINE RESULT ≠ FACT ≠ CANONICAL. Never replace the original value; show the transform and rule that produced every normalized candidate. Rank, Don’t Hide: return the relevant family, prioritize direct/exact hits first, then governed transforms, and avoid combinatorial spam. Human Gate remains ZURIEL.

Canonical example for this decision: query 456 should surface 456 exact, 1456 via leading-one remainder, 4560 via zero-scale, and the stored 45→56→456 overlapping reading, with each relation explicitly labeled by its rule/reading type.
