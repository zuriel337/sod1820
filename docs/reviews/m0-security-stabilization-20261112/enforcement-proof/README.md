- קובץ ההחלה **המשיך והוחל** על גוף חי בלי טריגר;
- קובץ ה־rollback **המשיך** כשטריגר ה־TRUNCATE חסר;
- טריגר מושבת עבר, ו־`CREATE OR REPLACE TRIGGER` **הפעיל אותו מחדש בשקט** (אומת: `D` ← `O`).

### 4. `SELECT … INTO` שיוצר טבלה

- `SELECT … INTO [UNLOGGED] [TABLE] שם` ברמה העליונה של קובץ (גם אחרי `WITH`) נספר כמבנה חדש, ודורש `-- OWNER-CHECK:` כמו `CREATE TABLE`.
- **לא נספר:** `INTO משתנה` בתוך PL/pgSQL, ‏`INSERT INTO`, ‏`MERGE INTO`, ‏`INTO TEMP`.
- **אומת על PostgreSQL 16:** בתוך PL/pgSQL זו השמה למשתנה, ו־`EXECUTE` של `SELECT … INTO` נכשל ("is not implemented"). לכן נסרקים רק ה־statements העליונים.

**מגבלות שנותרו בזיהוי SQL** (מתועדות גם בראש הפונקציה ב־`g1LawsSnapshotRules.mjs`). מה שיוצר מאגר בדרכים האלה **לא נראה ל־CI**:
1. גוף פונקציה או `DO` שנכתב כמחרוזת בגרש יחיד (לא ב־`$$`).
2. SQL דינמי שמורכב מחלקים (`'cre' || 'ate table'`, ‏`format()`, משתנה).
3. `CREATE MATERIALIZED VIEW` דינמי; SQL שנמסר כמחרוזת ל־`cron.schedule` או ל־`dblink_exec`.
4. `CREATE FOREIGN TABLE`, ‏`ALTER TABLE … SET SCHEMA`, ‏`ATTACH PARTITION`, ‏`CREATE EXTENSION`.
5. פקודות psql: ‏`\i` לא נפתח; `\gexec` מריץ תוצאת שאילתה.
6. זיהוי־יתר (הצד הבטוח): גוף פונקציה שיוצר טבלה נספר בעת ההגדרה, לא בעת הריצה.
7. **היקף:** נקראים רק `supabase/migrations` וקובצי ה־SQL של חבילות ההחלה. SQL אחר במאגר, וכל מה שרץ ישירות במסד, לא נראה. ה־baseline מכסה 41 טבלאות, לא את הסכמה החיה.

### 6. מה לא נאכף, ומה לא הוכח

- **פרישה של בעלים שיש לו ילדים פעילים** לא נחסמת במסד: טריגר שורה לא מבחין בין פרישה לבין החצי הראשון של החלפת גרסה. בדיקת התצלום ב־CI מסרבת לעץ שנוצר, והכתיבה הבאה לילד מסורבת במסד. חסימה בזמן ה־commit דורשת constraint trigger נדחה — **לא מומש; הצעה להכרעה.**
- **מי יכול לעקוף** (קריאה בלבד, 12.11): `public.nodes` והפונקציה בבעלות `postgres` — התפקיד של עורך ה־SQL ושל כלי ה־MCP. הוא יכול להשבית טריגר ולהחליף פונקציה. `service_role` אינו הבעלים ואינו יכול. `session_replication_role` — לסופר־יוזר בלבד.
- **אמיתות אישור** (שהרשומה היא באמת אישור של ZURIEL), וכפילות סמנטית — שער אנושי.
- **השער לא הורץ מול המסד החי.** כל ההוכחה במסד מבודד.
- **פער קטן בין השדות:** השער במסד קורא את `owner_routing.canonical_owner`; התצלום ב־CI קורא קודם את `compaction_v1.canonical_owner`. בחוק אחד (`research_workspace_law`) הם שונים (מסמך מול עצמו). לסשן החוזים.
- **`EXECUTE` של SQL דינמי במיגרציות**, ויצירת טבלה ישירות במסד (D2 של סשן החוזים: event trigger) — לא מומש בסבב הזה.

## מה נאכף טכנית, ומה נשאר בשער אנושי

| תחום | טכני (CI) | טכני (מסד, מוצע) | שער אנושי |
|---|---|---|---|
| בעלים שפרש או שאינו קיים | snapshot: הבעלים נפתר (חוק פעיל, ‏codex או קובץ שקיים); אינדקס: רק חוקים פעילים | חוק פעיל, או slug קיים ב־codex | — |
| שינוי חוזה קיים | גרסה, גוף ובעלים מושווים בין snapshot־ים; חוזה רשום משתנה רק עם רשומה חדשה | אין שינוי גוף ובעלים בלי גרסה; שושלת | **האם התוכן החדש נכון ומאושר** |
| מבנה חדש | קובץ חוזה מנותב; חוק חדש או שהופעל מחדש צריך רשומת אישור; טבלה או MV חדשים צריכים `OWNER-CHECK` (גם בחבילת ההחלה) | הכרעה מפורשת; בעלים חדש צריך הפניה לאישור | **האם באמת אין בעלים קיים מתאים** (כפילות סמנטית) |
| אישור | הצורה `work_log:<uuid>`; החוק קיים ב־snapshot; לא כפול | ההפניה קיימת ביומן ומזכירה את החוק | **שהרשומה היא באמת אישור של ZURIEL לשינוי הזה** |
| מחיקה | רשומות מתוארכות לא נערכות ולא נמחקות; ה־baseline רק מצטמצם | אין DELETE ואין TRUNCATE | — |
| עקיפה | אין required checks, ולכן CI מייעץ בלבד (B6) | ‏`DISABLE TRIGGER` / `CREATE OR REPLACE`, למי שיש לו הרשאת DDL | **אישור מפורש** לכל שינוי DDL והרשאות |

## מה **לא** הוכח
- ‏CI של GitHub על הראש החדש: מדווח בשיחה, לפי SHA.
- הרצת השער המוצע מול המסד החי (דורש `apply_migration`, באישור).
- כפילות **סמנטית**.
- שינוי שנעשה ישירות במסד ולא עובר ב־Git: ה־CI לא רואה אותו. לכן ה־snapshot המתוארך מתעדכן רק בקובץ מתוארך חדש.
