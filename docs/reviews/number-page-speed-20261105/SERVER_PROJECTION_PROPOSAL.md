# הקרנת דף המספר בצד שרת — הצעה (לא בוצעה)

> **סטטוס: הצעה בלבד, ממתינה לאישור נוסף של ZURIEL.** לא הופעלה מיגרציה, לא נכתב ולא נפרס קוד שרת, לא נגעתי ב־`middleware-core.js`, ב־`public-reading-deploy/`, ב־`api/og.js` וב־`api/public-document`, ולא שונה דגל או הרשאה. כל הנתונים כאן נמדדו (ראו [README.md](README.md) והקבצים ב־`evidence/`); מה שהוא הערכה מסומן **הערכה**.
> מצב חי נקרא מ־Vercel בכל פעולה; המסמך הזה אינו הרשאת פרסום.

## 1. למה (מה שנמדד)

| | נמדד |
|---|---|
| בקשות מסד לטעינה אחת של `/number/878` | 66 (62 קבצי JS בנוסף) |
| נפח מפוענח מהמסד | 889KB לפני, 667KB אחרי הצעדים הבטוחים (1.5MB ל־`/number/100`) |
| עומק התלות | כ־12 רמות עוקבות; שלוש שרשראות עצמאיות של כ־5 רמות שמסתיימות יחד: (א) משפחות ← קריאות לפי ביטויים ← registry וצמתי ישות, (ב) כרטיס התכנסות ← קריאה חוזרת לפי slug ← צומת ← קשתות ← יעדים, (ג) צומת ← קשתות ← צמתים קשורים ← מדיה |
| זמן עד תוכן מלא (מקומי, נתוני מסד חיים, קר) | דסקטופ כ־4.1 שניות, מובייל (CPU x4) כ־6.6 שניות; בחי 6–7 שניות |
| קריאה בודדת מהדפדפן | חציון 457ms. ה־preflight של CORS זול: חציון 53ms (נענה מקצה Cloudflare, `access-control-max-age: 3600`), ולכן **העלות היא עומק השרשרת כפול ה־RTT, לא ה־preflight** |
| איפה המסד | `ap-northeast-1` (טוקיו); פונקציות הפרודקשן רצות ב־`iad1` (אין `regions` ב־`public-reading-deploy/vercel.json`) |
| חשיפה לסורקים | 13,031 כתובות `/number/*` ב־`/sitemap.xml`; כל סריקה שמריצה JS עולה כ־66 קריאות ו־0.9MB |

מסקנה: קיצור רמה אחת בקוד הלקוח (עשיתי שתיים) חוסך 0.3–0.6 שניות אבל אינו משנה את הסוף, כי שלוש השרשראות מסתיימות יחד. כדי לרדת משמעותית צריך להוריד את כל הרמות יחד: **קריאה אחת, קרובה למסד**.

## 2. יעדים (נמדדים בכלי `tools/perf/number-page-measure.cjs`)

- בקשות מסד מהדפדפן לביקור ראשון: ≤ 3 (במקום 66).
- נפח מפוענח לביקור ראשון: ≤ 300KB (במקום 667–1,500KB).
- זמן עד תוכן מלא: ≤ 1.5 שניות בדסקטופ וכ־2.5 שניות במובייל (CPU x4) — **הערכה**, תימדד בשלב הצללית.
- עומס מסד לסריקה: ירידה של לפחות 90% בשאילתות לכל צפייה בעמוד שנמצא במטמון הקצה.
- אין החמרה ב־CLS (≤ 0.1, כיום 0.004–0.012) ואין שינוי בתוכן המוצג או בשיטות החישוב.

## 3. חלופות

| | מה | יתרונות | חסרונות / סיכונים | נדרש אישור |
|---|---|---|---|---|
| **A** | פונקציית SQL `number_page_projection_v1(p_value)` שמחזירה jsonb | קריאה אחת, אין תשתית חדשה | שכפול לוגיקת ההקרנה (כ־1,400 שורות JS ב־`entityHubProjection.js` וסביבתה) ל־SQL; סטייה סמנטית בין שני מימושים; מיגרציה גדולה; קשה לבדיקה ולגרסה | מיגרציית DB |
| **B1** | נקודת קצה ב־Vercel (Node) שמריצה את אותו קוד JS (`fetchEntityHubProjection`) ומחזירה JSON; מוגדרת ב־`hnd1` (טוקיו) לפי ה־`regions` לפי פונקציה ש־Vercel מתעדת; מטמון בקצה | אין סטייה סמנטית (אותו קוד); קריאה אחת; ניתן למטמון; מימוש קטן; fallback ללקוח | קובץ חדש בתיקייה מוגנת (`public-reading-deploy/api/`) ושינוי `vercel.json` שלה; פונקציה חדשה שעולה כסף; רק משתמש אורח (anon) | קובץ מוגן, תצורת region, פריסה |

| **D** | Proxy של Supabase על אותו מקור (rewrite) | מבטל preflight | הרווח קטן (53ms לבקשה), מעמיס את Vercel, מחייב `x-vercel-enable-rewrite-caching` בפרויקט ישן | `vercel.json` |

**המלצה: B1, בשלבים (סעיף 8).** A נשאר כאפשרות מאוחרת רק לשרשראות שיתבררו כאיטיות גם בקרבת המסד. D ו־E אינם מומלצים עכשיו.

## 4. ארכיטקטורה (B1)

**חוזה.** `GET /api/number-projection?value=<מספר שלם 0..9007199254740991>` ← `200 application/json`:

```json
{ "v": 1, "value": 878, "generatedAt": "<ISO>", "projection": { "...": "אותו מבנה ש־fetchEntityHubProjection מחזיר היום" } }
```

- `v` גרסת הסכימה; הלקוח מקבל רק גרסה שהוא מכיר, אחרת עובר ל־fallback.
- הלקוח מפעיל `fetchEntityHubProjection` המקומי אם: הדגל כבוי, הנקודה לא ענתה תוך 4 שניות, סטטוס שאינו 200, `v` לא מוכר או הגוף אינו JSON תקין. **הדף נשאר שלם גם כשהשרת מושבת.**
- **רק אורח.** השרת קורא עם מפתח ה־anon בלבד, כמו אורח; לכן משתמש מחובר (ש־RLS עשוי להרשות לו שורות נוספות, למשל `research_objects` עם `privacy_scope`) ממשיך במסלול הלקוח, או מקבל חבילת אורח ועוד קריאה אישית קטנה. ברירת המחדל המוצעת: מחובר ← מסלול הלקוח, ללא שינוי.
- **ריצה:** Node, `functions["api/number-projection.js"].regions = ["hnd1"]` (אותו אזור כמו המסד); שאר הפונקציות, כולל מסמך ה־SEO, נשארות ב־`iad1`.
- **מטמון:** `Cache-Control: public, s-maxage=300, stale-while-revalidate=3600` (או `Vercel-CDN-Cache-Control`), `Vercel-Cache-Tag: number-projection,number-<value>` לניקוי יזום. חוזה הטריות: עד 5 דקות פיגור לנתונים ציבוריים; **החלטה של ZURIEL** (כיום המסמך `no-store`).
- **שימוש חוזר בקוד:** `entityHubProjection.js` רץ ב־Node כמות שהוא (הכלי `tools/perf/number-projection-timeline.mjs` הריץ אותו על `878` והחזיר את ההקרנה המלאה). **ממצא שחייב טיפול לפני מימוש:** בריצה מ־Node (HTTP/1.1) שתי קריאות הרשימה הארוכות של `getValueFamilies` (`nodes`/`gematria_words` עם עד 300 ביטויים ב־URL של כ־18KB) נכשלו ב־`fetch failed` ו־supabase-js ניסה שוב בהשהיה; בדפדפן (HTTP/2) הן עוברות. המימוש בשרת חייב לחלק לרשימות קצרות (≤ 8KB ל־URL) או לעבור ל־RPC/POST, ולהיבדק מהסביבה היעד.
- **תצפית:** `Server-Timing` (זמן הקרנה, מספר שאילתות), ונקודת בדיקה בקנרית.

## 5. אבטחה ופרטיות

| איום | התמודדות |
|---|---|
| הצפת פרמטרים (13,031 ערכים כשרירותיים ← מטמון לא חם) | ולידציה (`/^\d{1,15}$/` ומספר שלם בטוח); כלל Firewall/rate limit לפי IP לנקודה (לאמת יכולת בתוכנית הנוכחית); coalescing של בקשות זהות במטמון הקצה; תקרת `maxDuration` |
| חשיפת מידע שאורח אינו רואה | מפתח anon בלבד, אותו RLS, בלי service role, בלי העברת cookies/Authorization של המבקר |
| הרעלת מטמון | מפתח המטמון הוא `value` ו־`v` בלבד; אין שיקוף כותרות/קלט מהמבקר |
| דליפת סודות | המפתח ב־env של הפרויקט, לא בקוד; מפתח ה־anon כבר ציבורי אך לא נכתב ללוגים |
| SSRF | אין URL שמגיע מהמבקר |
| שינוי בהתנהגות הבוט/ה־SEO | הנקודה `noindex` ואינה חלק מה־sitemap; מסמך `/number/N` נשאר כפי שהוא |

## 6. מיגרציה ושינויי DB

**B1 אינו דורש מיגרציה.** פריטים אופציונליים, **כולם דורשים אישור נפרד ואינם מופעלים**:

1. שורת דגל לכיבוי מיידי בלי פריסה (הסמנטיקה חייבת להיקבע במפורש; אין בקוד קריאה ל־`fx_*` כיום, ולכן לא מניחים סמנטיקה קיימת):
   ```sql
   -- טיוטה, לא מופעל. enabled=true פירושו: השרת מופעל. מתחיל כבוי.
   insert into public.site_flags (key, enabled, mode, message)
   values ('fx_number_server_projection', false, 'all', '')
   on conflict (key) do nothing;
   -- rollback: delete from public.site_flags where key = 'fx_number_server_projection';
   ```
2. אינדקסים: **לא מוצעים כעת.** קודם `EXPLAIN (ANALYZE, BUFFERS)` לשאילתות האיטיות מ־`hnd1`; רק אם יתברר צורך תוגש מיגרציה נפרדת עם בדיקה והחזרה.
3. חלופה A (אם תידרש): `public.number_page_projection_v1(p_value bigint) returns jsonb language sql stable` עם `grant execute ... to anon`, מיגרציה בקובץ משלה ובדיקת שוויון מול ההקרנה בלקוח על לפחות 50 מספרים חיים.

## 7. Rollback (מהיר לאיטי)

1. כיבוי הדגל (שורה אחת, ללא פריסה) ← הלקוחות עוברים מיד למסלול הקיים.
2. החזרת קומיט הלקוח (הוא רק קורא לנקודה ועובר ל־fallback).
3. החזרה לפריסת 2029 הקודמת ב־Vercel (alias, באישור מפורש; חזרה משחזרת קוד ולא מסד).
4. ניקוי מטמון הקצה לפי tag.
5. B1 לא משנה מסד, ולכן אין מה להחזיר שם. בחלופה A: `drop function public.number_page_projection_v1(bigint)`.
בדיקה שמוכיחה את ה־rollback: בדיקת fallback ללקוח (נקודה מחזירה 500, נתקעת, מחזירה `v` לא מוכר או גוף שבור) שבה הדף נשאר שלם.

## 8. שלבים

0. **נעשה:** מדידה וצעדים בטוחים בקוד הלקוח (ראו README).
1. **הצללה (בלי שינוי בחוויה):** נקודת הקצה פעילה אך הלקוח עדיין משתמש במסלול הקיים; ברקע, בזמן פנוי, הוא מביא גם את ההקרנה מהשרת ומשווה; מונה הבדלים בלבד, בלי נתוני משתמש. תנאי מעבר: 0 הבדלים סמנטיים על לפחות 500 צפיות ו־50 מספרים שונים.
2. **הפעלה לאורחים בדגל**, 5% ← 100%, עם מדידה (אותו כלי) ו־RUM.
3. אופציונלי: הטמעה במסמך להצגה ראשונה (חלופה E) — רק אחרי אישור לגעת בקבצים המוגנים.

## 9. בדיקות

- חוזה: ההקרנה מהשרת שווה (deepEqual, בלי `generatedAt`) להקרנה מהלקוח על fixture, ועל 50 מספרים חיים בהרצת השוואה.
- fallback: כל מצבי הכשל בסעיף 7.
- ולידציית קלט וגבולות (ערכים שליליים, גדולים, אותיות, `%00`).
- עומס: סימולציית סריקה של 500 כתובות מה־sitemap מול מטמון קר וחם; עלות שאילתות ל־Supabase ועלות הפונקציה.
- מדידת A/B עם `tools/perf/number-page-measure.cjs` (נוסף מצב שרת), בדסקטופ ובמובייל.
- בדיקה אחרי פריסה: הקנרית הקיימת, והוספת קריאה ל־`/api/number-projection?value=878`.

## 10. אישורים הנדרשים (שום דבר מזה לא בוצע)

1. כתיבת `public-reading-deploy/api/number-projection.js` ושינוי `public-reading-deploy/vercel.json` (קבצים מוגנים; `regions` לפי פונקציה).
2. הגדרת אזור `hnd1` לפונקציה (והשפעתו על עלות/השהיה).
3. חוזה טריות: עד 5 דקות פיגור לנתוני מספר ציבוריים, ומדיניות ניקוי.
4. שורת הדגל (סעיף 6.1) או מנגנון כיבוי חלופי.
5. כלל rate limit/Firewall לנקודה.
6. אישור פריסה לפי SHA מדויק, וקנרית ידנית אחרי כל מעבר alias.

## 11. מה לא נבדק

זמן ההקרנה כשהיא רצה ליד המסד (הערכה בלבד: כשישים שאילתות בעומק של כחמש רמות, מאות אלפיות שנייה סך הכול); עלות הפונקציה בפועל; ההתנהגות מול 13,031 כתובות; האם תוכנית Vercel הנוכחית מאפשרת rate limit בנקודה; ההשפעה על צריכת Supabase egress (צפויה לרדת).

מקורות תיעוד: [Function region](https://vercel.com/docs/functions/configuring-functions/region), [CDN cache](https://vercel.com/docs/caching/cdn-cache), [cache purge by tag](https://vercel.com/docs/caching/cdn-cache/purge).
