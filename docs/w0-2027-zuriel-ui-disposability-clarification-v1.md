# SOD1820 — W0 2027 ZURIEL UI DISPOSABILITY CLARIFICATION V1

**Status:** HUMAN-GATE PRODUCT DIRECTION · W0 INPUT · DOCS ONLY · NOT IMPLEMENTED · NOT A DELETE AUTHORIZATION  
**Date:** 2026-09-09  
**Owner verdict:** `EXTEND_EXISTING`

## 0. Purpose

This note corrects an important ambiguity in the 2027 planning package.

The current site was built iteratively. Existing screens, tools, bars, admin tabs and route groupings are not architectural commitments merely because they exist.

**Preserve canonical capability, identity, truth, provenance, security, authorization and Human-Gate semantics. Do not preserve current presentation by inertia.**

No code/data deletion is authorized by this note. Actual retirement happens only after capability, route/SEO, security and release checks.

---

## 1. Number Page — rebuild the experience, preserve selected valuable parts

The current Number Page is **not frozen** and is **not required to remain visually/structurally as it is**.

Target:
- Number remains a first-class focused World projection and one of the most important product surfaces.
- The Number experience may be redesigned **from the ground up** for the 2027 architecture.
- Valuable current sections/capabilities may be preserved, adapted or re-composed where they remain useful.
- W0 must identify those sections by capability/value; existence alone is not enough.

Therefore the correct disposition is:

**NUMBER = REBUILD EXPERIENCE FROM FIRST PRINCIPLES + PRESERVE SELECTED HIGH-VALUE CAPABILITIES/CONTENT/IDENTITY.**

This supersedes any presentation-only wording that says the Number Page can never be rebuilt/replaced. It does **not** authorize loss of canonical number identity, calculations, provenance, SEO/deep links or decision-approved research capabilities.

## 2. Current Heichal tool inventory — not protected

The current collection/order/layout of tools in the Heichal/research area was assembled during iterative development and has **no preservation priority by existence**.

### Explicitly important current product capabilities
- **ELS / letter skips** — preserve the proven canonical engine/capability and continuity; redesign its experience freely.
- **Number experience** — core product surface, but it belongs as a focused World projection, not as a Heichal tool.

### Everything else currently shown as a Heichal/research tool
Default W0 posture:
- `REVIEW`, `ABSORB`, `REPLACE` or `RETIRE` according to actual value and canonical owner.
- Do not keep a tool merely because it has a current route/card/tab.
- Do not discard a canonical underlying engine/method/trace merely because its present UI is disposable.

Heichal 2027 should expose the **best coherent research capabilities**, not preserve the current tool menu.

## 3. Forum — not a protected destination

The current Forum is **not** a required permanent product area.

Open product direction to test in W0:
- `בית המדרש` may become the natural home for **חידושים / contributions / research discussion** where that creates a simpler one-tree experience.
- Community/conversation can be projected where useful without forcing a standalone Forum product.

This is **not yet a final deletion decision**. Before retiring `/forum` or its data/capabilities, W0 must check:
- unique forum capabilities/content;
- route/SEO/inbound obligations;
- moderation/publishing semantics;
- whether Beit Midrash or another existing owner can absorb them without semantic loss.

Default disposition: **FORUM SURFACE = REVIEW FOR ABSORPTION / RETIREMENT; NOT PROTECTED.**

## 4. Admin / Command Room / current management system — fully replaceable UI

The entire current Admin / Command Room / management presentation may be replaced from A→Z.

This includes, subject to W0 capability parity and release safety:
- current `/admin` layout;
- current tabs/cards/rails;
- current Command Room visual structure;
- current management dashboards and navigation;
- current separation/grouping of controls;
- branch-only/admin-preview UX experiments.

What must **not** be lost merely because the UI is replaced:
- Human Gate authority;
- truth/governance/publication separation;
- security/authorization boundaries;
- source/intake provenance;
- review/candidate/canonical transition capabilities that are still valid;
- system operations/Metatron capabilities that remain valid;
- analytics/traffic/admin data owners;
- work_log coordination/provenance;
- auditability and destructive-action safeguards.

### 2027 target distinction
Do not preserve “Command Room” as an old screen/product just because the name exists.

At the semantic level distinguish:
1. **Admin Research / Human Gate Workspace** — sources, candidates, review, provenance, relation/workbench actions.
2. **System Operations / Metatron** — system health, diagnostics, traffic, deployment/operations intelligence.

They may share the same adaptive Admin shell and navigation, but they are different domains and must not merge truth semantics.

Default disposition:

**CURRENT ADMIN/COMMAND ROOM UI = REPLACE. UNDERLYING VALID CAPABILITIES = REUSE/ADAPT BY OWNER.**

---

## 5. W0 implication — capability-first pruning

W0 should no longer ask “how do we fit every current screen into 2027?”

It should ask:
1. What capability is genuinely valuable/canonical?
2. Who owns it?
3. Does it deserve a 2027 surface?
4. Can another existing surface/domain absorb it cleanly?
5. What route/SEO/user-data/security obligation must survive?
6. If none, can the old surface be retired after parity/safety verification?

This intentionally allows aggressive simplification of the site while preserving One Tree.

---

- **UI disposability ≠ data deletion.**
- **Surface retirement ≠ capability retirement.**
- **Existing tool ≠ required future tool.**
- **Existing route ≠ permanent information architecture.**
- **One Tree ≠ one giant screen.**
- **Number remains central, but its current layout is not sacred.**
- **ELS remains a core proven tool, but its current UI is not sacred.**
- **Forum and current Admin/Command Room are not protected product destinations.**
