### ✅ CONFLICT / NEEDS_HUMAN_DECISION — 2 rows found, both RESOLVED 22.8 by ZURIEL Human-Gate decision

1. **Method-count baseline mismatch — RESOLVED.** The contract chain repeatedly anchored on "**the current 13 active methods**" (Foundation Contract §8, §10, §11; `METHOD_LIFECYCLE_ALIGNMENT.md` §4) as the known-quantity baseline Methods Build #1 extends. But the live rule `canonical_methods_registry_law` (23.7.2026, still active) states the registry `public.gematria_methods` already has **20 rows**, of which 4 (אטבח·מילוי בלבד·מסתתר גדול·מילוי דמילוי גדול) were `in_engine=false` at time of writing; `gematria_values_engine_truth` says the `bidim` view must expose **14** method columns; `project_codex` (`gematria_engine` row) and `src/lib/gematria.js` describe **8** core dedicated columns (ragil/miluy/misratar/kadmi/gadol/siduri/atbash/albam). None of these numbers is "13."
   **ZURIEL's decision (22.8):** *"There is no single canonical fixed method-count number. `gematria_methods` is the method registry SSOT. Counts must always be qualified by capability/state, including where applicable: registered, approved/active, dispatchable, stored/indexed, displayed. Historical fixed counts such as 13/14/20/24 must not be treated as timeless canonical law. Preserve them as provenance/snapshots where relevant. Do not modify implementation merely to make historical counts agree."* Applied throughout the Foundation Contract and `METHOD_LIFECYCLE_ALIGNMENT.md` (see their own correction notes) — every bare "13 methods" reference is now capability/state-qualified language, with historical snapshot counts (like §2's "13 live methods" describing what `METHODS_EXPANSION_PHASE_1` actually ran against) preserved as-is, not deleted.
2. **Method-lifecycle stage ORDER discrepancy — RESOLVED.** `METHOD_LIFECYCLE_ALIGNMENT.md` §1 (echoed in Foundation Contract §8's "Definition of Done") had presented the pipeline as **discovered(known) → candidate → definition/reconstruction tested(reconstructed) → engine reproducible → Human-Gate → canonical**, i.e. a method becomes `candidate` *before* a reconstruction attempt is tested. But the live rule `method_lifecycle` states the order explicitly, with arrows, as **known → reconstructed → candidate → verified → canonical** — reconstruction attempted *before* `candidate` status.
   **ZURIEL's decision (22.8):** *"Canonical conceptual order: discovered/unresolved → definition reconstructed/defined → candidate → engine-tested/reproducible → Human-Gate approved → active. A historical method label with no sufficiently defined deterministic formula remains discovered/unresolved; do not represent it as an engine-ready candidate."* This confirms the live rule's sequence (with refined stage names) over the document's earlier, incorrectly-reordered table — `METHOD_LIFECYCLE_ALIGNMENT.md` §1 is corrected accordingly, and §3/Foundation-Contract-§14 reclassify **רגיל ישר והפוך** from `candidate` to `discovered/unresolved` (it has no defined formula, unlike ר"ת/ס"ת which do, were tested, and stay `candidate` correctly).

**Both resolutions are docs-only corrections, applied without destroying historical provenance** — no live rule text was written or altered (the live `method_lifecycle` rule needed no change; only the document restating it was wrong), no method activated, PR #166 not merged.
